# Changelog

Changes per release (newest first). The section of a version is added to its
GitHub release automatically when the release is built. Test versions are
pre-releases for test devices only.

## 0.2.0-beta.12

- **System: buildroot 2026.08.1** (2026.02 gets no more fixes), **kernel 6.18.58**, GCC 15.3. Newer packages, among them OpenSSL 3.6.5, curl 8.22, dropbear 2026.94, BusyBox 1.38, mdadm 4.6, ntfs-3g 2026.7.7, e2fsprogs 1.47.4, nfs-utils 2.9.1, rsync 3.5.0, SQLite 3.53, expat 2.9, Transmission 4.1.3, time zones 2026e and new CA certificates. System apps: **Tailscale 1.104.1** (1.104.2 needs a newer Go), **autobrr 1.89**, OpenVPN 2.7.8, Transmission 4.1.3, htop 3.5.1, strace 7.1, iperf3 3.21, nano 9.0. The real hdparm is in the firmware now (before: the BusyBox applet). ShareOS patches: mdadm (musl) refreshed, one uhttpd patch dropped (fixed upstream), libgpiod without GLib bindings. ksmbd-tools stays on the own 3.5.3 package (buildroot still has 3.5.2).
- **SMB: access through a group works (ksmbd-tools 3.5.3).** A user who only got a share through a group (`@family` in the share's access list) was refused over SMB – the Finder said "the original item can't be found" – while the same user named directly worked. ksmbd-tools 3.5.2, the version of the pinned buildroot, does not pass the supplementary groups of a user to the kernel, so the POSIX ACL entry `group:<name>` never applied ([ksmbd issue #461](https://github.com/namjaejeon/ksmbd/issues/461)); 3.5.3 is the first release that does. Buildroot has no newer ksmbd-tools, so the firmware uses the package `ksmbd-tools-shareos` (ksmbd-tools 3.5.3) of the ShareOS tree instead of buildroot's `BR2_PACKAGE_KSMBD_TOOLS`; it goes away when buildroot has caught up. Checked on a DNS-325 rev A1 with kernel 6.18: a user with the share only through a group opens it from macOS.
- **RAID: a mirror no longer starts with one disk when the second disk comes up late** ([#65](https://github.com/UniqueDroid/ShareOS/issues/65)). The DNS-325 brings its disks up one after the other (the second bay about 10 s after the first), and `shareos-storage boot` assembled the arrays before the second disk was there: the mirror ran on one disk (`[2/1] [U_]`) until a manual `--re-add`; a stripe or span stayed inactive. Now the members of the arrays in `/etc/mdadm.conf` are offered to `mdadm --incremental` as they appear, for at most 40 s – mdadm starts an array when its last member is there. After that, whatever is there is started (a really missing disk still gives a degraded mirror, logged as "RAID incomplete after 40s"). USB disks and foreign RAID members are not touched; without `mdadm.conf` there is no wait. New host test `tests/test-raid-wait.sh` with a fake mdadm (also in CI).
- **Storage → Health (SMART of disks and SSDs):** a page per disk with a rating (*GUT* / *ACHTUNG* / *KRITISCH*) and the reasons in plain words, temperature (with the lifetime maximum), running time, power cycles, motor start-ups, reallocated / pending / unreadable sectors, transfer errors (CRC – usually the connector, not the disk), error log, for SSDs the life left (device statistics or the vendor attribute) and the data written; all attributes as a table. **Self-tests** (short / long) from the page, with progress and the last result; by schedule (short test every Sunday or long test on the 1st of the month, 3:30) through `shareos-storage smart-test`, which reads the values again when the tests are done. The messages use the same rating (warning or error, with the reasons). rpcd: `shareos.storage smart_test`, `smart_schedule`; `smartctl -a -l devstat` instead of `-H -A -i`. New host test `tests/test-smart.sh` with smartctl JSON of a healthy HDD, a worn SSD and a failing HDD.
- **Disks may sleep, the flash is spared:** the storage page shows whether a disk is running or asleep (*AKTIV* / *SCHLÄFT*, `hdparm -C`, which does not wake it). The Paperless inboxes (every 2 minutes) are skipped while all disks below them sleep – nobody can have put a file there. A message for a problem that stays (checked every 10 minutes) only rewrites the message list in the flash once an hour instead of every time.
- **Interface:** a hidden tab or the app in the background no longer asks the box every few seconds (overview, header chips, messages, storage); it catches up when it is shown again – less load on the box and on the phone's battery.

## 0.2.0-beta.11

- **App permissions `sysinfo`, `netcheck`, `docker` and `tuya`** (each needs `files`, admin accounts only), so apps like SysMon, HomePing, DockerDeck and TuyaPulse show real data instead of sample values:
  - `sysinfo` – `ShareOS.sysinfo`: the box's values (CPU from two samples, memory, temperature, fan, load, network counters, drives with their use and standby, uptime, version) and the process list (user, memory, CPU ticks, command line); `kill(pid, signal)` ends a process – never init, kernel threads or what keeps ShareOS running (rpcd, ubusd, uhttpd, the board daemon, syslog). Through `/_shareos/cgi/sysinfo` (rpcd `shareos.appsys`).
  - `netcheck` – `ShareOS.netcheck.check([...])`: up to 32 checks side by side **from the box** – ping (loss, min/avg/max), TCP port open, HTTP/HTTPS answer with status, time and certificate check. Runs in the CGI `/_shareos/cgi/netcheck` with short time limits (rpcd `shareos.appnet` only checks the grant, so rpcd never waits for the network).
  - `docker` – `ShareOS.docker`: Docker hosts of the homelab through their Docker Engine API (`http://host:2375` or `https://host:2376`, up to 16, kept in `/etc/config/dockerhosts` and in the settings backup). Fixed calls only: version, info, images, containers, inspect, stats, logs (as plain text) and start/stop/restart/pause/unpause – no exec, no new containers, no other paths. Docker does not run on the box itself.
  - `tuya` – `ShareOS.tuya`: Tuya smart-home devices in the local network, **without the cloud** – `discover()` (their encrypted announcements on UDP 6666/6667), `status(device)` and `set(device, dps)` over TCP 6668 with the device's local key, protocol 3.3 and 3.4 (session key); 3.1 and 3.5 are not supported yet. The new program `/usr/sbin/shareos-tuya` (C, mbedtls, 13 KB) does the talking; the app keeps its devices and keys.
- ***Mein ShareOS* reworked:**
  - The tab *Darstellung* is now *Einstellungen* (`#/settings`; the old address still works) and holds *Passwort ändern* next to the look settings.
  - *Speicher* on the start page is a table over the full width: one row per drive of the personal folder and the shares – what lies there, own use and limit, a bar (own limit, or the drive when there is none) and the free space of the drive (`shareos.me` gives `volumes` and the drive of each share).
- **"Teilen mit" on the phone:** the app installed from the browser (Android/Chrome; iOS does not offer this to web apps) appears in the share menu. What is shared goes into the folder `Geteilt` in the personal folder of the account that is logged in – photos and files as they are, a link or text as a small `.txt` file; a name that is taken gets " (2)". Only for accounts with a personal folder. Manifest `share_target`, the service worker keeps the shared files until the interface uploads them (also after a login), rpcd `shareos.me share_ticket`. Needs a trusted certificate (as for installing the app at all).
- **File dialog of the apps (`ShareOS.fs.pick`) with the shares:** accounts without *Dateien* now see their personal folder and their shares there as well (by their rights; read-only shares are not offered for saving). The app's own folder stays first and keeps its data; in the dialog it is called *App-Daten*. `ShareOS.fs.roots()` marks the entries with `personal` and `share`. *Dateien* still decides about the file browser in the interface.

- New test `tests/test-sysperms.sh` (with a fake Docker API and a fake Tuya device built from tinytuya's own frame and cipher code).
## 0.2.0-beta.10

- **FAV APPS – favourite apps per account:** a small star on every app card (Apps → Installed, also in the table view; *Mein ShareOS* → My apps) marks an app as favourite. The favourites appear as an icon bar **FAV APPS** directly above *Status* in the overview, above the installed apps and at the top of *Mein ShareOS*; a click opens the app. Every account has its own favourites (root too). Under Appearance each account switches the bar on or off and chooses icons with names or icons only. Stored per account (`fav`, `fav_bar`, `fav_text` – root in `shareos.ui`, the others in their `accounts` section), set through `shareos.me fav_set`.
- **System → Appearance in two columns** on screens from 900 px; on narrower screens the panels stay one below the other, now over the full width.
- The tabs Apps, Cloud and Paperless no longer carry the "NEU" badge.
- **Login message:** the line on the console and in `/etc/motd` (SSH, web terminal) names version, model and web address – e.g. `ShareOS 0.2.0-beta.10 on DNS-320L-rev-Ax: web interface http://192.168.1.20/, link 1000 Mbit/s.` – instead of "phase-1 test system ready … (password: shareos)".
- **Buttons: `shareos-buttons` reads the events again (DNS-325, DNS-320L).** On a DNS-325 rev A1 none of the buttons did anything: the program ended at once and wrote nothing to the log. Two causes: the kernel names the input device after the device-tree node – `gpio_keys` on this box, `gpio-keys` on the DNS-320L – and the program only looked for `gpio-keys`; and ucode reads files through stdio, which asks the kernel for a first chunk of 15 bytes, while an event device refuses reads under one event (16 bytes, `EINVAL`). The program now accepts both names and reads the events through `dd bs=16`; `S05board stop` ends that `dd` through its PID file (`/var/run/shareos-buttons-dd.pid`). Checked on the DNS-325: power, reset and USB buttons, and one `dd` left after a restart of the service. The reset and USB buttons use `gpio-keys` on every model and the kernel and ucode are the same everywhere, so they were affected on the DNS-320L too (seen with beta.9: `shareos-buttons` ended at once, a press of the USB button left no trace) and probably on the DNS-320 (not tried); the power button of the DNS-320L and DNS-320 rev B is polled by `shareos-board` and not concerned, the one of the DNS-320 rev A is a gpio-key like the DNS-325's (not tried). New tests for the device name and the PID file in `tests/test-buttons.sh`.
- **Apps keep the files of admins in their own folder:** for admin accounts the folders an app sees (`ShareOS.fs`) now start with a personal folder – the account's own home (`/mnt/<drive>/home/<name>`), for root `/mnt/<apps drive>/home/root` (made on first use, 0700). Apps that store their data in the personal folder (ShareNotes, Webpad …) no longer write it to the top of a drive. The drives themselves stay reachable for admins as before. Files an app already wrote to the top of a drive stay there; move them by hand if wanted, e.g. for ShareNotes on the drive `daten` (in System → Terminal or over SSH):

  ```sh
  mkdir -p /mnt/daten/home/root && chmod 700 /mnt/daten/home/root
  mv /mnt/daten/notes /mnt/daten/home/root/
  ```

  If your apps drive is not `daten`, use its name instead; other apps' folders (e.g. `webpad`) move the same way.

## 0.2.0-beta.9

- **Tailscale starts by itself:** the daemon now runs as soon as the system app `tailscaled` is installed and after every restart – it waits for the sign-in, and a box that was signed in connects again by itself. Before, only an app's *Verbinden* started it.
- **Services of system apps are declared in their `app.json`:** `"service": { "control": "tailscale", "on_install": "start", "delay": 5 }` – ShareOS starts it at boot (`/etc/init.d/S90services`, after its delay, in the background), right after installing if asked, and stops it when the app is removed or the box shuts down. The work is done by the firmware's controller `/usr/sbin/shareos-<control>`, which states what it can do (`shareos-service: boot start stop-all`); a package cannot bring its own, so only reviewed code starts daemons as root. One init script and no removal hooks replace `S93tailscale`, `S94vpn`, `S95transmission`, `S96dlna` and `/usr/lib/shareos/apphooks` – renaming a system app can no longer break its start. Packages built before carry no `"service"` yet; ShareOS knows their entries.
- **Services → Status / Autostart** list the services of installed system apps (Tailscale, VPN, Transmission, media server) with their state; start, stop and switching the autostart off work for them as for the other services (the names stay `tailscale`, `vpn`, `transmission`, `dlna`).
- **System apps are submitted to the ShareOS repository** (`sysapps/`), web apps to ShareOS-Apps: `sysapps/README.md` explains both kinds with an example each – a program (`tree`) and a service with its controller (`mosquitto`) in `docs/examples/sysapps/`.
- **Copying in apps shown in the page works:** the frame of an app inside the ShareOS page (permission `embed`) and the web terminal now allow the clipboard (`allow="clipboard-read; clipboard-write"`, plus fullscreen and autoplay for players). Before, a copy button in such an app failed with "The Clipboard API has been blocked because of a permissions policy".
- **Apps keep their data on the box also for accounts without "Dateien":** an app with the permission `files` opened by such an account gets one private folder of its own – `/mnt/<apps drive>/.shareos/userdata/<account>/<app>` (the account's, 0700) – as its only folder in `ShareOS.fs` (root `app`, `private: true`). The account's personal folder, the shares and the file browser stay closed, and other permissions (`torrent`, `media` …) still need "Dateien". Before, `ShareOS.fs` was missing and apps like ShareNotes fell back to the browser. Removing the app removes these folders; deleting an account with its data removes them too.
- **autobrr (download automation):** the system app `autobrr` (autobrr 1.84, 32 MB with its web interface, on the apps drive) watches IRC announce channels and RSS feeds and picks releases by your filters. One autobrr for the whole box: `shareos-autobrr` runs it as its own user `autobrr` on 127.0.0.1:7474 with a Go memory limit (`GOMEMLIMIT=48MiB`), its database on the apps drive; the first start signs it up (user `admin`) and makes an API key for ShareOS (root only). Found torrents go to the Transmission of one account: autobrr's action *Watch dir* writes them into the hand-over folder `/mnt/<apps>/.shareos/autobrr-drop` (the account's, group `autobrr`, 2770), which that account's Transmission watches. Optionally autobrr's own web interface on `http://<box>:7474` (its own login, password set from ShareOS). Starts after installing and at boot (`"service": { "control": "autobrr" }`), listed under Services.
- **Permission `autobrr`** for apps (needs `files`), admin accounts only: `ShareOS.autobrr` – status, start, set (on/off, web interface, account for the hand-over), password, accounts, log and `api(method, path, body)`: autobrr's REST API through `/_shareos/cgi/autobrr` with the key of ShareOS (rpcd `shareos.appautobrr`; not `/api/keys` or `/api/auth`). The app itself comes from ShareOS-Apps.
- **DNS-325: first start on real hardware (rev A1).** The beta.7 `.bin` for the DNS-325 made the box restart in a loop: the kernel booted, printed `INITRD: 0x00800000+0x001ff000 overlaps in-use memory region - disabling initrd`, found no `/init` and panicked (`panic=10` restarts after 10 s), so neither the first installation nor the rescue system ever ran. The initramfs of the DNS-325 is now loaded at `0x01000000` instead of `0x00800000` (`post-image.sh` makes one header per model; it checks the address in each finished image, and `tests/check-initrd-address.sh` checks the bundles in CI). With the new address the DNS-325 boots from flash. The DNS-320L and the DNS-320 keep `0x00800000` until someone has tried the new address on them (a wrong address is a reboot loop that needs a serial console); the kernel is the same on all models, so what is in use at `0x800000` on the DNS-325 depends on the board or its U-Boot – not found yet.
- **First installation / `shareos-install-ubi` on the DNS-325:** the tool refused the `image` partition ("unexpected size 0x06600000, expected 0x06400000"). The DNS-325 has 102 MB there (no `my-dlink` partition), the DNS-320L 100 MB; both are accepted now, any other size is still refused. The DNS-320 rev A shares the DNS-325's flash layout in Alt-F's device trees (not seen on hardware yet). New test `tests/test-install-ubi.sh`.
- Checked on a DNS-325 rev A1: model and RAM (256 MB), 1 Gbit/s Ethernet, temperature sensor, clock, USB, the 6 flash partitions, the LEDs, the three fan presets (quiet, balanced, cool) and the box starting again by itself after a power cut (with the drives stopped by `shareos-storage shutdown` first). The power, reset and USB buttons do not work on this box yet (`shareos-buttons` finds no input device; a separate change fixes it), and a complete first installation from a freshly flashed `.bin` still needs a test ([DEVICES.md](docs/DEVICES.md)). A DNS-325 that already runs beta.7 and restarts in a loop needs a serial console to recover (the old initramfs is in its flash). The DNS-320L, DNS-320 rev A/B boxes are not tested with the new address yet.

Large system apps of older versions move there at the next start. Packages are unpacked on the drive, so they never take room on the flash. The flash (about 40 MB for settings and system apps) stays free.

## 0.2.0-beta.6

- **Snapshots (Storage → Snapshots):** dated states of a share, of the personal folders or of a whole drive on another drive – hourly, every 6 hours, daily or weekly. Every snapshot looks like a full copy; files that did not change are hard links to the snapshot before and take no space twice (rsync `--link-dest`, the way rsnapshot works, without Perl). What to keep: the last N in any case (also those taken by hand) plus the newest of each day, week and month (e.g. 3 · 7 days · 4 weeks · 6 months). Exclusions (`*.tmp`, `/Downloads/`), *Back up now*, stop (the next run continues the half snapshot), list of the snapshots, open one in the file browser to restore, delete one, log, message when a snapshot fails. The snapshots are in `/mnt/<drive>/Snapshots/<job>/<YYYY-MM-DD_HHMMSS>` (root only, 0700); the target needs hard links (ext4, Btrfs – not FAT32/exFAT). A drive saved into itself leaves its `Snapshots` folder out.
- App SDK: `ShareOS.lang` – the language of the ShareOS interface, for apps with their own translations (e.g. Transmission 1.2).
- rsync 3.4 in the firmware (without OpenSSL, 0.2 MB) and `ionice`: snapshots run at the lowest CPU and disk priority.
- **Media server (Services → Media server):** MiniDLNA 1.3.3 (ReadyMedia) as the system app `minidlna` (2.8 MB, in the release as `.sapp`): TVs, receivers, game consoles and apps like VLC find the box in the network (DLNA/UPnP AV) and play music, videos and pictures from the chosen shares – per share everything or only music, videos or pictures, with its own name in the network. New files show up by themselves (inotify); *Read everything again* rebuilds the library. The library is kept on the drive of the apps area, so a restart does not read everything again. The page shows the number of tracks, videos and pictures and the players that were connected. The firmware starts and stops the server (`shareos-dlna`, `S96dlna`); removing the system app stops it. It only reads the folders and shows the chosen shares to every device in the network, without sign-in.
- **VPN client (OpenVPN) for the box:** the system app `openvpn` (OpenVPN 2.6.20, 2.4 MB, in the release as `.sapp`) and the app NetTunnel (ShareOS-Apps) connect the box to a VPN – e.g. to the office or a VPN provider. The kernel now has tunnel support (`CONFIG_TUN`). Profiles (`.ovpn`) are cleaned on import: nothing that runs programs (`up`/`down` scripts, plugins, `script-security` …), no settings of the box itself (log, status, user, chroot, management …), keys and certificates only inline; server profiles are refused. OpenVPN always runs with `--script-security 1`. User name and password for `auth-user-pass` are kept beside the profile (root only, `/etc/shareos/vpn`). Per profile: all traffic of the box through the tunnel, or only the VPN networks (the pushed default route is ignored); one profile can connect when the box starts (`S94vpn`). Removing the system app ends the connection.
- **VPN server (OpenVPN) on the box:** reach home from anywhere – phone or laptop connect to the box. The box makes its own small CA on first use (EC keys with mbedTLS, `tls-crypt` key, valid 10 years, in `/etc/shareos/vpn/server`, root only) and one certificate per device; NetTunnel gives a complete `.ovpn` profile per device for the OpenVPN app. Only known devices get in (`--ccd-exclusive`): removing a device locks it out at once. Settings: on/off (also after a restart, `S94vpn`), address in the internet (DynDNS), port, UDP/TCP, VPN network (not the home network), optionally the whole home network (pushed route + IP forwarding; the router needs a route back). Connected devices with VPN address and traffic; header chip **VPN-SERVER · n Geräte**.
- **Permission `vpn`** for apps (needs `files`): `ShareOS.vpn` – list, status, log, importProfile, set, remove, connect, disconnect, and `ShareOS.vpn.server` – status, set, log, addDevice, profile, removeDevice – through `/_shareos/cgi/vpn`; admin accounts only (a VPN changes the network of the whole box).
- **Status in the header:** next to *Online*, chips show what is running – the VPN (connected, address), the user's Transmission service, the media server (when installed) – and a click opens the app. **Permission `status`** (needs `files`): an app may show one short state of its own (`ShareOS.status.set({ text, state, ttl })`, max. 24 characters, ok/warn/err/info); it disappears by itself after at most 10 minutes unless the app sets it again, and only the account that opened the app sees it. Users see their chips in "My ShareOS". System → Appearance: which chips this browser shows.
- **System menu in a new order:** General, Appearance, Network, Messages, Logs, Terminal, Time, Power & reset, Firmware; *System* opens on General. *About* is now at the end of General (the old address `#/system/about` leads there).
- **Shares by rights for the file browser and apps:** users with "Dateien" see their personal folder **and the shares they have rights to** (before: only the personal folder) – in "My ShareOS → Files" and in apps with the permission `files` (`ShareOS.fs.roots()` now also says `ro`). In read-only shares the box refuses every change (new folder, rename, move, delete, upload, saving from apps, FFmpeg output, Transmission download folder); the file browser greys the buttons out. A personal folder is no longer required for this.
- **Share rights as POSIX ACLs:** the rights of a share (read & write / read only, groups, guest, NFS) are set as ACLs on its folder and everything in it, with default ACLs for new files; everybody else gets nothing. So Linux itself holds every program of a user to them – SMB, apps, Transmission, cloud jobs –, not only SMB and the web interface. Changed rights are applied in the background; taken-away rights are gone everywhere. Kernel: ACLs for ext4 and Btrfs; `setfacl`/`getfacl` in the firmware. exFAT, NTFS and FAT have no Linux rights: there only SMB and the web interface check them.
- Fix: Transmission (and FFmpeg) did not start for users, only for admins – system apps installed from the web interface were in a folder only root could read (rpcd works with umask 077). `/opt/shareos` is now always readable for every account and repaired at boot; Transmission names the cause if an account cannot run it.

## 0.2.0-beta.5

- **Media jobs on the box – FFmpeg as a system app:** `ffmpeg` (FFmpeg 6.1.5 with `ffprobe`, LAME and Opus, about 2.6 MB, in the release as `.sapp`) converts audio and puts videos into another container. The box runs the jobs itself, in the background, one after another, at the lowest priority and with the account's rights (admins: root, like their file browser): files belong to the account, storage limits apply. Videos are not re-encoded – the box's ARM CPU has no FPU, that would take many times the length of the film. The app MediaTranscoder (ShareOS-Apps) uses it.
- **Permission `media`** for apps (needs `files`): `ShareOS.media` – `probe` (format, length, tracks of a file), `start` (a job from fixed choices: `audio` to MP3, M4A/AAC, Opus, FLAC, WAV or the track as it is; `remux` to MP4, MKV, MOV, TS, WebM; cut with start and length), `jobs` (state and progress), `cancel`, `remove` – through `/_shareos/cgi/media`. No ffmpeg command line from an app reaches the box: the box builds the arguments, reads and writes only inside the account's folders, never overwrites a file (the result appears under its name when it is complete), only local files (no network protocols in this FFmpeg), at most 10 waiting jobs per account. Removing the system app cancels running jobs.
- **App store in sections:** the available apps are grouped by category (Media, Office, Network, Tools, System …) with a filter per section and a search field.
- **Bash** as a system app (GNU bash 5.2, 0.7 MB): `bash` in the terminal; the box's default shell stays ash.

It runs with the account's rights (admins: root, like their file browser), keeps its state on the account's drive (not in the flash), downloads into the account's folders and starts again after a restart of the box. The app Transmission (ShareOS-Apps, by @SamuelSilvaG) controls it.
- **Permission `torrent`** for apps (needs `files`): `ShareOS.torrent.rpc(method, args)` reaches the account's daemon through `/_shareos/cgi/transmission`. The daemon has no TCP port for its remote control (Unix socket only); the proxy passes only what a remote control needs – no scripts, no RPC settings, no torrents from local files – and folders only inside the account's own (`<root>/<path>` like `ShareOS.fs`).
- `ShareOS.fs.pick({ folder: true })`: the file dialog of the box chooses a folder.
- **Apps bring what they need:** `"requires": ["transmission-daemon"]` in `app.json` – installing the app installs the required app from the store first (also for an uploaded package); the store asks before removing an app another one needs. System apps (nano, htop, strace, iperf3, transmission-daemon) are in the store catalog now (ShareOS-Apps lists them from the ShareOS releases). Services come only with the firmware: a package never starts a daemon by itself.
- libevent: a request on a Unix socket no longer ends the program (musl's `getnameinfo` does not know `AF_UNIX`).
- **Login page shows the first sign-in** (user `root`, password `shareos`) as long as root still has the factory password; it disappears once an own password is set and comes back after an access reset. The password is public anyway, so the hint gives nothing away (asked in #28).
